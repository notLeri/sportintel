# ADR-004. Сначала правила и шаблоны; локальная LM — опциональный ускоритель

- **Статус:** принято
- **Дата:** 2026-10-07
- **Затрагивает:** SRS §2, ARCHITECTURE §1.3 / §19, CONV §1–§4, §10, задачи фаз 2–4 (таблица ниже), новая задача T3.15

## Контекст

Проект должен работать **без денежных вложений**. В исходных спецификациях каждая «умная» операция завязана на платные API: Claude (обогащение, серая зона кластеризации, summary, черновик, конфликты) и Voyage (эмбеддинги). Пока неизвестно, нужен ли редакции ИИ вообще: возможно, хватит уникальных событий и аккуратно отформатированных постов-заготовок, которые человек выбирает и дописывает.

## Решение

1. **Базовый режим — `rules`, он бесплатный и полностью детерминированный.** Каждый шаг конвейера, где раньше был ИИ, получает реализацию на правилах:

   | Шаг | Режим `rules` (по умолчанию) | Режим `llm` (опционально) |
   |---|---|---|
   | Обогащение статьи (`enrich_article`) | `RuleEnricher`: вид спорта по разделу URL, категориям RSS и словарю; сущности и турнир по алиасам справочника; маркеры слухов и clickbait по словарям; relevance по взвешенным правилам `enrich_rules` | Промпт `enrich_article/v1` |
   | Эмбеддинги | Нет (`embedding = NULL`) | Локальная модель через Ollama (`bge-m3`, 1024) |
   | Кандидаты и скоринг кластеризации | Лексическая похожесть заголовков (pg_trgm) + общие сущности + турнир + окно времени; синдикация — как в BE-T2.15 | + косинус по centroid |
   | Серая зона кластеризации | Создаётся новое событие со связью `possible_duplicate` к лучшему кандидату; человек объединяет (merge, BE-T4.3) | Промпт `cluster_adjudicate/v1` |
   | Summary и нейтральный заголовок события | Экстрактивно: заголовок и лид **основной статьи** (OFFICIAL → самая ранняя tier A → самая ранняя), `TextOrigin=source` | Промпт `event_summary/v1` + grounding |
   | Черновик Telegram | **Шаблон** (`TemplateDrafter` → тот же `DraftOutput` → тот же `assemble`), `TextOrigin=template` | Промпт `telegram_draft/v1` + grounding |
   | Конфликты источников | Выключены (claims в режиме правил не извлекаются) | Задача `events.detect_conflicts` |

2. **Лента «фейкового Telegram» (новая задача T3.15).** Для каждого уникального события с relevance ≥ `drafts.auto_min_relevance` система **сама** готовит черновик по шаблону. Черновики показываются на странице `/feed` как сообщения канала Telegram. Вкладка **«Предложения»** содержит события, ещё не выбранные человеком. Вкладка **«Канал»** — посты `READY`/`PUBLISHED`, в том виде, в каком канал выглядел бы для читателя. Пользователь берёт сообщение в работу, правит, копирует и отмечает как опубликованное, либо отклоняет. Автоматический черновик **не меняет статус события**: это предложение, а не решение.

3. **Локальная LM подключается одним переключателем, без изменения кода модулей.**
   - **Где работает LM (инфраструктура, env).** `AI_PROVIDER=ollama`, `OLLAMA_URL` указывает на любую машину с [Ollama](https://ollama.com): ту же VM, отдельную локальную VM или сервер, ноутбук разработчика (по туннелю, например Tailscale). Модель по умолчанию — `qwen2.5:7b-instruct` (хорошо знает португальский), эмбеддинги — `bge-m3` (размерность 1024 совпадает со схемой CONV §6.3).
   - **Какие шаги её используют (бизнес, `app_settings.ai_routing`).** У каждого шага `rules|llm`, у черновика `template|llm`. Admin переключает шаги в UI (BE-T4.10) без деплоя. Так можно включать LM постепенно, начиная с самого полезного шага, и сравнивать качество.
   - **Максимальный режим.** Когда LM включена на всех шагах (`drafts.auto_mode=llm`), лента получает уже написанные моделью посты с цитатами `[n]`, и человеку остаётся проверить и нажать «Копировать».
   - **Деградация.** Если LM недоступна (таймаут, circuit breaker, невалидный ответ после repair), шаг **автоматически откатывается на правила или шаблон**, а не падает. В `/me.system_status` выводится «LM offline — работаем на правилах».

4. **Платные провайдеры остаются портами, но не реализуются в MVP.** Адаптеры Anthropic (BE-T2.3) и Voyage (BE-T2.6), бюджет в долларах (BE-T2.5) и цены (`ai_pricing`) откладываются до момента, когда появится бюджет. Порты `LlmClient` и `EmbeddingClient` не меняются, поэтому подключение потом — это только новый адаптер.

5. **Порядок работ.** Сначала строится путь `rules`: фазы 2–3 дают рабочий продукт без LM. LLM-ветки всех задач собраны в **фазу L (опциональную)**, она выполняется после фазы 3 или параллельно, если нужна.

## Почему

- **Ноль затрат на старте.** Никаких ключей API. LM, если понадобится, бесплатна: работает на своём железе.
- **Проверяем гипотезу дёшево.** Если шаблонов и правил хватает, ИИ не нужен совсем. Если нет — видно, на каком шаге он окупается: аналитика (T4.15) показывает долю правок черновиков и precision HIGH по режимам.
- **Предсказуемость.** Правила объяснимы (rationale = список сработавших правил), их легко править через admin. Галлюцинаций нет: шаблон цитирует источник дословно.
- **Архитектура почти не меняется.** Контракты `EnrichOutput`, `DraftOutput`, `assemble`, `clustering.score` (режим без эмбеддингов уже описан в BE-T2.14) остаются прежними. Меняются реализации и маршрутизация.

## Альтернативы

- **Сразу Claude с жёстким бюджетом.** Это стоит денег, и неизвестно, нужно ли вообще.
- **Только локальная LM, без правил.** Требует железа (7B-модель на CPU — десятки секунд на статью) и даёт непредсказуемое качество. Без правил нет fallback, и при падении LM конвейер встаёт.
- **Локальные эмбеддинги без LLM (sentence-transformers в worker).** Возможно, но тянет torch в образ (~1–2 ГБ) и CPU в worker. Ollama изолирует модели в отдельном процессе или машине. Этот вариант можно рассмотреть позже, через тот же порт `EmbeddingClient`.

## Компромиссы и риски

- **Кластеризация без эмбеддингов** хуже склеивает статьи об одном факте с разными заголовками. Компенсация: связь `possible_duplicate`, ручной merge, калибровка порогов (BE-T2.20) на реальных данных.
- **Relevance по правилам** грубее модели. Компенсация: веса в `app_settings` правит admin, override в UI (BE-T4.5), замер precision HIGH (T4.15).
- **Черновик по шаблону** — это заготовка, а не готовый пост. Его дописывает человек. Метрика «доля правок черновиков» покажет, стоит ли включать `telegram_draft=llm`.
- **Конфликты источников (AC-11)** в режиме `rules` не обнаруживаются. **AC-11 выполняется только при включённой LM** (фаза L). Это осознанное сужение MVP: reliability всё равно ограничивает доверие к одиночным и слуховым источникам.
- **Локальная LM медленная на CPU.** Очередь `ai` для Ollama работает с параллелизмом 1 (`OLLAMA_CONCURRENCY`). Интерактивная генерация может занимать минуту; FE показывает прогресс (как в FE-T3.12), а шаблонная версия доступна сразу.

## Когда пересмотреть

- Доля правок шаблонных черновиков > 80 % или precision HIGH < 60 % на пилоте (INFRA-T5.10): включить LM на соответствующем шаге.
- Появился бюджет и нужно качество выше локальной модели: реализовать адаптер Anthropic (отложенная часть BE-T2.3) и бюджет (BE-T2.5).
